## Summary

- **The outcome sentence of S-22 is, in its literal reading, already the code since S-04 (2026-10-01) and S-13 (2026-10-17).** The tap is handled by the optimistic React island `src/components/tasks/CheckoffControl.tsx:64-105`: the row, the viewer's grid cell and the Leaderboard total flip at the tap (`:71-75`), the request goes out through `sendCheckoff` (`src/lib/checkoff-client.ts:26-66`), and every non-`saved` answer either reloads (`stale`, `expired`) or rolls the three back and shows an inline `<p role="alert">` with "Could not save. Try again." or "This task is no longer available. Reload the page." (`:15-18`, `:95-104`, `:152-156`). The grid cell is not clickable: `GridCell.tsx:25-32` is a `<span>`, and `ViewerGridCell.tsx:16-17` follows the island's store. The roadmap's unknown is therefore a question about changing an existing optimistic design, not about adding one; S-04 chose the island "over the recommended form POST" (`context/archive/2026-10-01-checkoff-and-leaderboard/plan-brief.md:29`).
- **Where the view can still end in a state that is not the server's (this inspected path).** On a timeout (`CHECKOFF_TIMEOUT_MS = 15_000`, `checkoff-client.ts:6`, `:33-36`) or a lost response, the island rolls back and says "Could not save" while the database may already hold the row; S-04's phase-5 review accepted this as "one more tap converges" (`reviews/impl-review-phase-5.md:63`), because a repeat tick is a quiet 23505 → ok (`src/lib/checkoffs.ts:54-67`). Until that tap or a reload, the grid shows `open` for a saved period. No code path re-reads the true state after a failure.
- **Where a failure still vanishes (this inspected path).** A failure that never reaches the Worker (offline, DNS, timeout, a dropped connection) ends in `catch { return { kind: "failed" } }` (`checkoff-client.ts:61-63`) and is shown to the user, but reported nowhere: the island has no `sendBeacon`, no `/api/client-errors` code and no browser Sentry (S-08 excluded client-side capture on purpose, `context/archive/2026-10-02-observability-swallowed-errors/plan.md:41`). The server side of the S-08 contract holds on every branch inspected: no returned `{ error }` is dropped in `checkoff.ts`, `uncheck.ts` or `checkoffs.ts` (table in Detailed Findings). The channel for a client code exists: `POST /api/client-errors` accepts a closed list of 7 codes (`src/lib/pwa/register.ts:7-16`) and reports `client.sw.<code>` (`src/pages/api/client-errors.ts:33`).
- **"Fast" has no measurement in the repo.** Structurally, one save is 4 sequential upstream calls from the Worker: GoTrue `getUser` and the `nicknames` read in the middleware (`/api/tasks` is in `PROTECTED_ROUTES`, `src/middleware.ts:10-18`, and not in `NICKNAME_ROUTES`, `:20`), then the `tasks` pre-read (`checkoff.ts:31-35`, kept so that a stale submit gets `gone` instead of a 42501, `:30`) and the insert or delete. The optimistic flip hides this from the user; the only visible trace of the wait is the Undo or Mark-done button at 50 % opacity (`PENDING_STYLE`, `CheckoffControl.tsx:22`), with no spinner and no text. `/dashboard` wall time was left unmeasured on 2026-10-01 by the owner's decision (`context/changes/deployment/deployment-plan.md:181`); Sentry has no tracing (`grep tracesSampleRate|startSpan src/lib/sentry.ts` empty) and `wrangler.jsonc:20` enables Workers observability (logs), which is operator-side and not the analytics the privacy policy excludes.
- **No recorded observation of a slow or failed save exists.** The milestone's source is the owner's description of 2026-10-19 ("Szybkość i błędy zapisu", `roadmap.md:26`); no document, device row or log excerpt records a concrete slow or failed tick (`grep -i "wolno|slow|latenc|opóźni"` over `deployment-plan.md`, `open-items.md`, `health-check.md`, `roadmap.md`: only the unmeasured-CPU row). The S-21 frame notes the owner had not seen the problem first-hand for that slice (`context/archive/2026-10-19-grid-state-feedback/frame.md:42`).
- **Files S-22 owns, by three prior plans:** `src/components/tasks/CheckoffControl.tsx`, `src/lib/checkoff-sync.ts`, `src/components/tasks/ViewerGridCell.tsx` (S-20 plan `:16`, S-21 plan `:35`), plus `src/lib/checkoff-client.ts` by content. None of the first three has changed since 0a10058 (S-13, 2026-10-17; `git log` on the three files and `checkoff-client.ts`). S-21 reserved "the moment of the server answer" for S-22 (`2026-10-19-grid-state-feedback/frame.md:62`).
- **Server-wait would cut against a settled requirement.** The PRD guardrail "Odznaczenie tasku musi być natychmiastowe (bez zauważalnego opóźnienia)" (`context/foundation/prd.md:40`), US-01 "wynik jest natychmiast widoczny" (`:48`) and FR-013 "Komórka widza w bieżącym okresie zmienia się od razu po odznaczeniu" (`:123`) are satisfied today by the flip at the tap. A wait-for-server tick would put the 4-call round trip in front of the flip with no measurement showing it unnoticeable. That is a frame/owner decision, recorded here as the conflict it is, not decided.

## Detailed Findings

### The save path today, from tap to database

- Row control: `src/components/dashboard/TaskRow.astro:61-71` renders `<CheckoffControl client:load>` for the viewer's own task. The control is two plain forms, `method="POST" action="/api/tasks/uncheck"` (`CheckoffControl.tsx:116`) and `/api/tasks/checkoff` (`:132`), each with a hidden `task_id` (`:117`, `:133`) and `onSubmit={handleSubmit}`. Before hydration or without JavaScript the browser posts natively and the route answers a 302; after hydration `handleSubmit` calls `event.preventDefault()` (`:65`).
- Handler (`:64-105`, bytes verified at faa5fca): `if (pending) return;` (`:66`); `setChecked(next)`, `publishChecked(taskId, next)`, `setPending(true)`, `setMessage(undefined)`, `publishDelta(viewerId, delta)` (`:71-75`); `await sendCheckoff(action, taskId, recurrence === "once" ? null : currentPeriod)` (`:77-81`); `saved` → `setPending(false)` (`:83-86`); `stale` → `window.location.reload()` with the button still pending (`:87-92`); otherwise rollback of the three (`:95-97`, focus returned only if the user has not moved on, `:94`); `expired` → reload (`:98-102`); `rejected`/`failed` → `setPending(false); setMessage(FAILURE_MESSAGES[result.kind])` (`:103-104`), rendered as `<p role="alert" className="text-destructive basis-full text-xs">` (`:152-156`). No retry button, no automatic retry, no report.
- Client protocol (`src/lib/checkoff-client.ts`): form-encoded body, `Accept: application/json`, `credentials: "same-origin"`, `redirect: "manual"`, `keepalive: true`, an `AbortController` at 15 s (`:33-49`). Mapping (`:52-62`): opaque redirect or 3xx → `expired`; 403 or 404 → `rejected`; any other non-200 → `failed`; a body without `ok: true` and a string `period` → `failed`; `period` ≠ expected → `stale`, else `saved`; a thrown error (network, abort) → `failed`. `once` tasks pass `expectedPeriod = null` and are `saved` on any 200 (`:60`).
- Grid link: `src/lib/checkoff-sync.ts:51-58` holds the per-task checked map; `ViewerGridCell.tsx:16-17` renders `done`/`open` from it, `initialState` while the store is empty; only the viewer's current cell is an island (`CheckoffGrid.astro:83-87`, comment `:23-24`).
- Routes (`src/pages/api/tasks/checkoff.ts`, `uncheck.ts`, same shape): no user → 302 `/auth/signin` (`:13-16`); `formData()` + `normalizeUuid` (`:18-23`, null → info `checkoff.invalid_id` → `invalid`); no client → `not_configured` (`:25-28`, no route line; the middleware reports `auth.not_configured` once per isolate, `src/middleware.ts:37-40`); `getTask` (`src/lib/tasks.ts:14-26`, throws on `{ error }` `:20`; null → info `checkoff.task_gone` → `gone`, `checkoff.ts:30-35`); `checkOff(supabase, user.id, task, new Date())` (`:37`), `unknown` → error `checkoff.failed` (`:38-40`); `catch` → error `checkoff.exception` → `unknown` (`:42-45`).
- Data layer (`src/lib/checkoffs.ts`): `checkOff` `:57-67` computes `periodKeyFor(task.recurrence, now)` from the server clock (`src/lib/streak-rules.ts:42-53`, Warsaw calendar day, Monday key for weekly) and inserts; `error.code === "23505"` is a quiet idempotent `ok` (`:54-55`, `:65`). `uncheck` `:79-98` deletes the period (daily), the Warsaw week (`:90-92`) or everything (`once`) and answers `ok` on 0 rows with info `uncheck.nothing_removed`. `failureOutcome` `:36-51`: 42501 → error `<action>.forbidden` → `forbidden`; 23503 → info `<action>.not_enrolled` → `forbidden`; any other code → `{ kind: "unknown", error }` (the `status` argument is dropped at `:50`).
- Response (`src/lib/checkoff-response.ts:10-16`, `:26-35`): JSON mode when `Accept` contains `application/json` (`src/lib/http.ts:2-4`): 200 `{ ok: true, period }` or `{ ok: false, error: <kind> }` with the kind's status, `Cache-Control: no-store`; form mode: 302 to `/dashboard` (success, `gone`), `?error=forbidden` (`invalid`, `forbidden`), `?error=not_configured`, `?error=unknown`.
- Database (`supabase/migrations/20261002090000_create_task_checkoffs.sql`): PK `(task_id, user_id, period)` and FK to `task_participants` with cascade (`:28-35`, both unnamed in the migration); grants insert/select/delete only (`:43-46`); policies `task_checkoffs_insert_self` with `user_id = auth.uid()`, a visible task and `period between (utc date) - 7 and (utc date) + 1` (`:54-68`), delete on own rows only; no trigger or function computes or validates the period (`:8-11`: "Trust-based by design"). A server-computed Warsaw period lies inside the window on every day (UTC date or UTC + 1, Monday at most 6 days back), so a window 42501 can come only from a direct API call (derived from the two definitions, not tested; `tests/integration/task-checkoffs.test.ts:151-164` tests the window edges with raw clients, not the handler).

### States the view can show that are not the server's (this inspected path)

1. **False failure after a commit.** Timeout or lost response → rollback to `open` plus "Could not save. Try again." while the row exists. Accepted in S-04 (`impl-review-phase-5.md:63`): a repeat tap is a 23505 → `saved`, so the view converges on the next tap; nothing converges it without a tap or a reload. The reverse (undo timed out after the delete committed) rolls back to `done` while no row exists; a repeat undo matches 0 rows → `saved`.
2. **`stale` keeps the optimistic state and reloads without a message** (`CheckoffControl.tsx:87-92`); after the reload the server's day is truth. Offline, the reload shows the browser's error page. S-21 left the after-midnight snapshot unfixed on purpose (`2026-10-19-grid-state-feedback/plan.md:40`).
3. **`rejected` on a task that is gone** rolls back to `open` and asks the user to reload; the row disappears only on reload. The message is the only cue.
4. **Check-off then undo racing** (two tabs, or `keepalive` after a navigation): single statements with no lock; if the delete runs before the insert commits, the undo answers `ok` + `nothing_removed` and the row then exists. Reasoned from READ COMMITTED semantics by the server worker; no test exercises it.
5. **Double tap** cannot double-save: `if (pending) return;` (`:66`) plus `aria-disabled:pointer-events-none` (`:22`); the server side is idempotent anyway (23505 → ok, pinned by `scripts/smoke.mjs:2107-2111`, `tests/integration/task-checkoff-flow.test.ts:113-120`).

### What "fast" is made of

- Per save, from the Worker, 4 sequential upstream calls: `auth.getUser()` (`src/lib/auth-state.ts:30-42`), `getOwnNickname` (`src/middleware.ts:56`; `/api/tasks` is protected, `:10-18`, and only the nickname page and route are exempt, `:20`), `getTask` (`checkoff.ts:31`), insert or delete. None run in parallel; no RPC, no transaction. The following dashboard load, when one happens (form mode, `stale`, `expired`), is 2 stages / 5 queries plus the middleware's 2 (`src/lib/dashboard-data.ts:76-88`).
- The `getTask` pre-read exists so that "a stale submit gets `gone` instead of the policy's loud 42501" (`checkoff.ts:30`); the insert policy itself re-checks task visibility (`task_checkoffs_insert_self`). Removing the pre-read would change the `gone` branch and its info line, which `tests/integration/data-routes.test.ts:966-1130` pins.
- Nothing in the repo measures any of this: no tracing in `src/lib/sentry.ts`, the CPU/wall row of `/dashboard` left unmeasured by the owner (`deployment-plan.md:181`), `test-plan.md:57-58` "Ocenia się je ręcznie lub obserwowalnością, nie testem", `:226` "Re-evaluate, jeśli pojawi się skarga na opóźnienie". Workers Logs are enabled (`wrangler.jsonc:20`); whether the owner counts an operator-side timing as "pomiar" is not recorded.
- The user-visible wait is the pending style only: `aria-disabled` + `opacity-50`, no spinner, no text (`CheckoffControl.tsx:20-22`, `:124-125`, `:139-140`). A tap before hydration takes the native path: a full round trip and page load before anything changes on screen.

### Precedent for reporting a client-side failure

- `src/lib/pwa/push.ts:56-59` `report()` sends a fixed code with `navigator.sendBeacon(CLIENT_ERRORS_PATH, code)` (`:177`), used on reminders subscribe/unsubscribe failures (`:112`, `:129`, `:142`); `src/lib/pwa/register.ts:46` does the same for the service worker. ## Architecture Insights

- The whole interaction is "optimistic island over a native form": the same two forms work without JavaScript through POST + 302, and the island takes over on hydration. Every outcome kind the server can produce is already classified on the client; what is missing is not classification but (a) convergence to the server's state after a `failed` that may have committed, (b) any trace of a client-side failure, and (c) any visible pending signal beyond opacity.
- The server is the source of truth only after a reload; the client store (`checkoff-sync`) has no "saved" flag and no event log, so nothing outside the control can know whether the server confirmed.
- Reporting is one-directional today: the server reports what reaches it; the browser reports only PWA codes. The `/api/client-errors` route is the one sanctioned way to add a client code, with a closed list and a fixed `client.sw.` prefix.
- Both routes are idempotent by design, which makes a retry (manual or automatic) safe; the comment at `checkoff-client.ts:22` says so, but no caller retries.
