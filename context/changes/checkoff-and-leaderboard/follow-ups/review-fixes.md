# Review follow-ups: checkoff-and-leaderboard

Queued by `/10x-impl-review checkoff-and-leaderboard phase 1` (`reviews/impl-review-phase-1.md`, F9) and `phase 2` (`reviews/impl-review-phase-2.md`, F2). Apply them when the named phase is planned or implemented.

- **Phase 3, `uncheck` for weekly tasks**: delete the rows of the whole current week (`period >= Monday` and `period <= Monday + 6`), not only the row whose period equals `periodKeyFor(...)`. `snapshotOf` snaps any weekly key to its Monday, so a non-Monday row inserted directly through the API (inside the RLS window, trust-based per the PRD) would keep the week "Done" after Undo. **Applied in Phase 3 (`05cc307`)**: `uncheck` in `src/lib/checkoffs.ts` deletes the whole current week for `weekly` tasks, covered by a flow test.
- **Phase 4, `Leaderboard.tsx` and `dashboard.astro`**: export `UNKNOWN_MEMBER` from `src/lib/leaderboard-rules.ts` and use it for the displayed fallback (and for `dashboard.astro:101` and `:144`), so the sort fallback and the displayed fallback cannot drift apart. **Applied in Phase 4 (`e4c7b18`)**: `UNKNOWN_MEMBER` is exported from `src/lib/leaderboard-rules.ts` and used by `Leaderboard.tsx` and by `dashboard.astro` (participants fallback and Members row).
- **Phase 6, the `/dashboard` reading (row 6.6)**: note the wall time of a `/dashboard` request from Workers Logs next to its CPU time in `context/changes/deployment/deployment-plan.md`. The unfiltered `task_checkoff_periods` read is database time and does not count as Worker CPU. If the wall time grows with the number of groups, apply the `group_id` recipe from Performance Considerations in `plan.md` (a `create or replace view` that restates `with (security_invoker = true)`).
