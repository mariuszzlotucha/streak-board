**Why `status: partial`**: every question below is answered, but three items cannot be closed from the repo or the docs: (1) the hosted Supabase dashboard values, above all "Confirm email" (owner-only, see Open Questions); (2) no run of the real Google flow exists, because there are no Google credentials, so runtime claims about `/authorize` and the consent screen are read from source and docs, not observed; (3) Google's own pages contradict each other on two points (section 1). ## Research Question

Derived from `context/changes/google-login/frame.md` (confirmed problem statement and "What changes for /10x-plan") and the three S-07 unknowns in `context/foundation/roadmap.md:109-111`. The slice adds "Sign in with Google" next to the existing e-mail+password login. The research asks, without designing the slice:

1. What does Google require for a sign-in-only OAuth client (scopes `openid`, `email`, `profile`): consent-screen fields, home page, privacy policy, Testing versus production, and is a home page or privacy policy needed before the slice (the roadmap's "must S-09 come first" question)?
2. How does Supabase Auth with the installed `@supabase/ssr` start and finish the Google PKCE flow on the server, and what exactly comes back to the app on success, denial and failure?
3. How would the existing e-mail flow, the shared `/auth/callback`, the `join_code` cookie, the reporting helpers, the tests, the smoke script and the release gate interact with it?
4. What happens when the same e-mail already has an e-mail+password account?
5. What did earlier changes and documents already decide?

## Summary

- **Google console (docs fetched 2026-10-05).** For an External app in publishing status "Testing" that requests only `openid`/`email`/`profile`, Google's audience page says users need not be on the test-user list, see no warning message and do not hit the 7-day expiry; the 100-test-user cap is stated for Testing in general (section 1). The home page and privacy-policy links are "recommended" in Testing and "required for all external production apps". Google's own definition of a production app excludes an app "not shared with anyone else or … used by fewer than 100 people (all of whom are known personally to you)". Two Google pages contradict the exemption and the verification rule (section 1); the exemption was not tested live.
- **Roadmap unknown on S-09 (`roadmap.md:111`).** No Google document ties the consent screen to a landing page. What Google asks for is a public home page that is "not … only a login page", describes the app, and links a privacy policy hosted on the same domain. `/` already shows product copy (section 9), but no privacy or terms page and no footer link exist anywhere in `src/` or `public/`. S-09 lists S-07 as its own prerequisite (`roadmap.md:137`), so S-09 cannot precede S-07 without reordering; the piece Google asks for is a small privacy page, not the S-09 landing page.
- **Consent screen shows `<project-ref>.supabase.co`.** Supabase's Google guide says users see the project domain unless a custom domain is set. `supabase.co` is on the Public Suffix List (checked by a worker), so the owner cannot prove Search Console ownership of it (inference). Google says the brand name and logo appear only after brand verification (section 1).
- **Starting the flow on the server works with the existing `createClient`.** In the installed `@supabase/ssr` 0.12.7 and `auth-js` 2.116.0, `signInWithOAuth` called server-side returns `{ data: { url } }` without redirecting (`GoTrueClient.ts:4845,4849`) and writes the PKCE verifier through the client's `setAll` before it resolves (`ssr/src/cookies.ts:485-500`). The app's `setAll` (`src/lib/supabase.ts:15-19`) forwards cookies to Astro, which attaches them to a returned redirect (reported, not run). It drops the cache-header argument that `@supabase/ssr` passes.
- **The callback contract is the main code change.** `src/pages/auth/callback.ts:17-19,25-26,30-31` sends every failure to `/auth/signin?error=link_expired`. A provider denial arrives as `?error=access_denied&error_description=…` with no `code` and no `error_code`, in the query and duplicated in the fragment (GoTrue v2.196.0 `external.go:812-837,862-865`). A flow older than 300 s, or an unknown `state`, does not come back to `redirectTo` at all: it goes to the Site URL root with `error_code=bad_oauth_state` (section 3).
- **Three places pin the no-code redirect** to exactly `/auth/signin?error=link_expired`: `tests/integration/auth-callback.test.ts:45-48`, `scripts/smoke.mjs:346-351`, `.github/workflows/ci.yml:149-153`. The unit test context lacks `routePattern` and `locals`, so a call to `requestFields(context)` would throw there (`src/lib/log.ts:120-130`).
- **Identity linking.** With a verified Google e-mail equal to an existing user's e-mail, GoTrue adds a Google identity to the same `auth.users` row, so the id and every foreign key stay (section 5). For an UNCONFIRMED e-mail+password account it removes the password and the other identities first. With hosted "Confirm email" off, `config.Mailer.Autoconfirm` makes every provider e-mail count as verified and password sign-ups are auto-confirmed, so that protection does not apply; the hosted value is not recorded in the repo.
- **Existing-account side effects reach the e-mail forms.** A Google-only user gets `invalid_credentials` from `signInWithPassword` (the same code as a wrong password), and the app has no password-reset flow in `src/`. `signUp` with an e-mail that a Google user holds returns an obfuscated user or `user_already_exists` depending on `Mailer.Autoconfirm || Sms.Autoconfirm`; `signup.ts:29` redirects the obfuscated case to `/auth/confirm-email`.
- **`join_code` is not touched by the auth routes** (`signin.ts`, `signup.ts`, `callback.ts`, `middleware.ts`: no reference). The cookie is Lax, host-only, 1 h (`src/lib/join-code.ts:14-20`); the Google round trip consists of top-level navigations, so by the cookie's attributes it is sent on the return. No test walks an invite through the callback.
- **Local and CI.** The repo has no `[auth.external.google]` block. In CLI v2.117.0 (the version CI pins), an enabled provider with an unresolved `env(...)` secret gives only a warning; an empty `client_id` is fatal. GoTrue builds the Google provider by fetching Google's OIDC discovery document, so a local `/authorize` needs outbound access to `accounts.google.com`; not run.
- **Frame corrections.** `/` is no longer the starter template (commit `35b08ea`); the callback checks the presence of `error` and `error_code` but reads no value; `docs/reference/contract-surfaces.md` does not exist in this repo (section 6).

## Detailed Findings

### 1. What Google requires (primary sources, fetched 2026-10-05)

A worker downloaded the pages with `curl`, stripped the HTML and string-matched every quote below. I re-fetched `support.google.com/cloud/answer/15549945` myself and matched the three quotes marked (re-read). Other quotes rest on the worker's match.

**Testing status, External user type** (`support.google.com/cloud/answer/15549945`, "Manage App Audience"):

- "Projects configured with a publishing status of Testing are limited to up to 100 test users listed in the OAuth consent screen." (re-read)
- "The only exception to this behavior is if your app requests a subset of the following: name, email address, and user profile (through the userinfo.email, userinfo.profile, openid scopes or their OpenID Connect equivalents ). For such requests, your users do not need to be in the trusted user list, they will not see a warning message, and their authorizations will not expire after 7 days. If your app uses Sign in with Google to authenticate users then this exception also applies." (re-read)
- The same page's general text says a test user sees a warning before authorizing. The overview page's Testing row (updated 2026-05-22) puts the exemption and "Users see a warning UI indicating the app is in testing" in one cell, and `support.google.com/cloud/answer/13464323` says the unverified screen and the 100-user cap apply to apps "in development/testing/staging". These do not reconcile; the exemption was not tested live.
- Internal needs an organization: `support.google.com/cloud/answer/13461325` says it is "only available for apps created under a Google Workspace Organization". A personal-Gmail project cannot choose it.

**Branding fields** (`support.google.com/cloud/answer/15549049`, "Manage OAuth App Branding"):

- User support e-mail: "requires you to specify an email address". App name and logo appear on the consent screen "only if your app has been verified"; without verification "only your application domain will be visible to users".
- Home page, privacy policy, terms of service links: "It is recommended that you provide these links"; "Note : These links are required for all external production apps. You will not be able to submit your app for verification if it is missing these links." Other Google pages call the terms of service "optional" (`…/production-readiness/policy-compliance`, `…/brand-verification`).
- Home page: "must be hosted on a verified domain you own"; "must describe your app's functionality to its users. Your homepage can not be only a login page"; must link the privacy policy, "and this link should match the link you added on your OAuth consent screen configuration". Privacy policy: "should be hosted within the domain that hosts your homepage" and "must disclose how your app accesses, uses, stores, and/or shares Google user data".
- Google states no minimum length or format for either page. Whether a bare minimum page would pass a human or automated review is not documented.

**What counts as production** (`developers.google.com/identity/protocols/oauth2/policies`, last modified 2026-08-05): "a 'production' app … isn't for personal use. An app is considered to be for personal use if it's not shared with anyone else or will be used by fewer than 100 people (all of whom are known personally to you)." and "Some policies and requirements only apply to production apps." `support.google.com/cloud/answer/13464323` adds that a personal-use app of fewer than 100 users needs no verification, but "will need to complete a verification, if they want to grow their user base beyond 100".

**Production, External, unverified, non-sensitive scopes only** (overview page, updated 2026-05-22): "Any Google user can access. Strongly discouraged. Because the app has not completed brand verification, the app's name and logo are not displayed on the consent screen. Additionally, for apps requesting sensitive or restricted scopes, unverified app warnings (Danger UI) will be displayed to users, and a hard cap of 100 total users applies." The 100-user cap is defined for "unapproved sensitive or restricted scopes" (`…/15549945`).

**Is verification mandatory for sign-in-only production apps? The sources conflict.**

- Not mandatory: `support.google.com/cloud/answer/13463073`: "If your app utilizes only non-sensitive scopes, it is not mandatory for your app to complete the app verification process. However, if you want your app to display an app name and logo … brand-verification."
- Mandatory: `developers.google.com/identity/verification/authentication-policy-compliance` (Sign in with Google): "If your application utilizes Sign in with Google for authentication only, you must submit your application for brand verification." `…/oauth2/policies`: "For production apps, brand information must be verified."
- Not resolved by any primary text I found; the consequence for an unverified production app without a home page or policy is not stated either.

**OAuth client** (`support.google.com/cloud/answer/15549257`; Supabase's guide for the field values):

- Type "Web application" (Supabase guide). Authorized redirect URI: the Supabase callback `https://<project-ref>.supabase.co/auth/v1/callback`. Redirect URIs must use HTTPS except localhost. Google needs JavaScript origins only for client-side JS calls, yet Supabase's guide says to add the app URL there.
- "It may take 5 minutes to a few hours for changes made to these settings to take effect".
- Authorized domains: "All domains used in your project, whether in the branding page or client configuration pages must be pre-registered here." Brand verification adds that the list "needs to include the redirect URIs or JavaScript origins authorized in your 'Web application' OAuth client types", with ownership proven in Search Console. Whether the console refuses to save a redirect URI whose domain is not listed, while the app is in Testing, is not stated by any primary source.
- `supabase.co` is a public suffix (the worker read `publicsuffix.org/list/public_suffix_list.dat`), so `<ref>.supabase.co` is its own registrable domain. My inference is that Search Console ownership of it cannot be proven with a default Supabase URL; Google does not say so. `…/policy-compliance` recommends using "your own domain" instead of a provider's shared domain.

**Changes in 2025-2026** (`developers.googleblog.com/en/usability-and-safety-updates-to-google-auth-platform/`, 2025-04-28, and the policies page): OAuth settings live in a "Google Auth Platform" section (Branding, Audience, Clients, Data Access); the client secret is shown once at creation; "OAuth clients inactive for 6 months will be automatically deleted" (restorable for 30 days; unused means no token exchanges and no configuration edits). I found no new limit specific to unverified sign-in-only apps; that is absence of evidence from the pages reached, not proof.

**User Data Policy** (`developers.google.com/terms/api-services-user-data-policy`, "Last updated February 15, 2024"): "You must publish a privacy policy that fully documents how your application interacts with user data. You must list the privacy policy URL in your OAuth client configuration when your application is made available to the public." The policy names Google Sign-In as in scope.

### 2. Supabase: starting the flow on the server (installed: `@supabase/ssr` 0.12.7, `auth-js` and `supabase-js` 2.116.0, Astro 7.3.2, `package-lock.json`)

- `createServerClient` forces `flowType: "pkce"`, `autoRefreshToken: false`, `detectSessionInUrl: false`, `skipAutoInitialize: true` after spreading `options.auth` (`node_modules/@supabase/ssr/src/createServerClient.ts:165-175`). `src/lib/supabase.ts:10-22` passes no `cookieOptions` or `auth` options.
- `signInWithOAuth` → `_handleProviderSignIn` redirects only `if (isBrowser() && !options.skipBrowserRedirect)` (`node_modules/@supabase/auth-js/src/GoTrueClient.ts:4845`) and returns `{ data: { provider, url, flowId }, error: null }` (`:4849`). In Workers and Node `isBrowser()` is false (`lib/helpers.ts:34`, reported), so `skipBrowserRedirect` is not needed server-side.
- The generated URL is `${supabaseUrl}/auth/v1/authorize?provider=google&redirect_to=…&code_challenge=…&code_challenge_method=s256` (`_getUrlForProvider`, `GoTrueClient.ts:5692-5734`, reported).
- The verifier is written to cookies while `signInWithOAuth` runs: the server storage `setItem` calls `applyServerStorage` (hence `setAll`) for any key ending in `-code-verifier` (`ssr/src/cookies.ts:485-500`, re-read). Reported: up to three items per start (`<key>-flow-<flowId>-code-verifier`, `<key>-flows-code-verifier`, legacy `<key>-code-verifier`; `lib/helpers.ts:339-342`, `:366-388`), the storage key is `sb-<first host label>-auth-token` (`supabase-js/src/SupabaseClient.ts:333`, re-read), so `sb-wzpgyobsomvjyfrngyuu-auth-token` on the hosted project.
- Cookie attributes come from `DEFAULT_COOKIE_OPTIONS`: `path: "/"`, `sameSite: "lax"`, `httpOnly: false`, `maxAge: 400 days`, no `secure`, no `domain` (`ssr/src/utils/constants.ts:3-10`, re-read); `applyServerStorage` always writes `maxAge` as that default (`ssr/src/cookies.ts:620-624`, re-read). The same mechanism already writes the verifier for `signUp` with `emailRedirectTo` (`src/pages/api/auth/signup.ts:19-20`), which production sign-ups exercised on 2026-09-30 and 2026-10-02 (owner-reported, `context/changes/deployment/deployment-plan.md:191`).
- `setAll` receives `(cookies, headers)`; the headers are `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0`, `Expires: 0`, `Pragma: no-cache` (`ssr/src/cookies.ts:665-670`, re-read). The app's `setAll` ignores the second argument (`src/lib/supabase.ts:15`), as it does for the sign-in and sign-up cookies today.
- Cookies set with `context.cookies.set` before `return context.redirect(...)` are attached to the returned response (`astro/dist/core/middleware/astro-middleware.js:42`, `core/cookies/response.js`; reported, not run). The `@supabase/ssr` docs warn that when the verifier `Set-Cookie` "doesn't reach the browser, the callback can't exchange the code for a session".
- Exchange without the verifier cookie: `exchangeCodeForSession` throws `AuthPKCECodeVerifierMissingError` inside its try block (`GoTrueClient.ts:2057-2059`, re-read) and returns it as `{ error }` with `status` 400 and `code` `pkce_code_verifier_not_found` (`lib/errors.ts:269`, re-read; status reported). No request reaches GoTrue in that case (reported), so the one-time code is not consumed. The server path reads the fixed `-code-verifier` key (`lib/helpers.ts:397-408`, re-read).
- Two overlapping starts (double click, two tabs): the fixed key mirrors the most recent flow, so the first callback fails with `bad_code_verifier` (reported, medium confidence).

- Error details are in the query string and, with a code comment "TODO: deprecate returning error details in the query fragment", also in the fragment (`external.go:818-835`). Neither `src/pages/index.astro` nor `src/components/Welcome.astro` nor `Layout.astro` nor `Topbar.astro` reads the query string (rg: no `searchParams` or `Astro.url`), so a state error that lands on `/` is invisible to the user in the inspected tree.

A Worker calling `exchangeCodeForSession` and `signInWithPassword` therefore shares one IP bucket unless `Sb-Forwarded-For` forwarding is enabled for the project (hosted setting, unknown).

### 4. Redirect allow-list and Site URL

- `GetReferrer` returns `redirect_to` if valid, else the `Referer` if valid, else the Site URL (`utilities/request.go:75-89`). `IsRedirectURLValid` accepts any URL with the Site URL's scheme, host and port (port ignored for loopback hosts), any loopback IP literal, and otherwise a match against the allow-list with the fragment cut off (`:94-139`).
- Entries are compiled as globs with `.` and `/` as separators (`conf/configuration.go:1214-1219`, reported). Docs: "`*` matches any sequence of non-separator characters; `**` matches any sequence of characters". So `https://streakboard.app/**` matches `https://streakboard.app/auth/callback`, also with a query string (GoTrue test `request_test.go:279-283`, reported). An entry without a wildcard stops matching once a query string is appended (auth-js `lib/types.ts` comment, reported). The worker is about 90% sure `**` also matches an empty tail; not executed.
- Consequence for production: the hosted Site URL is `https://streakboard.app` (owner-reported 2026-10-02, `deployment-plan.md:190`), so by the Site URL rule an app callback on that origin is valid even without the wildcard entry; the wildcard matters for other origins.
- Consequence locally: `supabase/config.toml:154-156` sets Site URL `http://127.0.0.1:3000` and `additional_redirect_urls = ["https://127.0.0.1:3000"]` (the comment says "_exact_ URLs", the code uses globs). The app runs on `http://localhost:4321` per the README, `ci.yml` and `playwright.config.ts` (worker report). `localhost` differs from the Site URL host `127.0.0.1`, so by `request.go:94-139` a `redirectTo` on `http://localhost:4321/auth/callback` falls back to the Site URL locally unless it is allow-listed, whereas `http://127.0.0.1:4321/…` passes by the loopback rule.
- The app computes `emailRedirectTo` from the request origin only: `${new URL(context.request.url).origin}/auth/callback` (`src/pages/api/auth/signup.ts:19`); `astro.config.mjs` has no `site` or `security.allowedDomains`. `README.md:257` states the allow-list rule for sign-up.

### 5. Identity linking and the e-mail+password interplay (GoTrue v2.196.0)

- `DetermineAccountLinking` treats an e-mail as verified when `email.Verified || config.Mailer.Autoconfirm` (`internal/models/linking.go:67-68`, re-read). With no verified e-mail it decides CreateAccount (`:103-117`, re-read). Otherwise it links to an existing user with the same lower-cased e-mail (`:122-176,200-213`, reported). Google's `email_verified` comes from the ID token (`provider/oidc.go:91-105`, reported).
- Linking inserts a new `identities` row with the existing `user_id`; no new `auth.users` row is created and the session is minted for that user (`external.go:234,310-315`, reported). The user's `raw_user_meta_data` is merged with Google claims (`full_name`, `name`, `avatar_url`, `picture`, …; same-named keys overwritten; `models/user.go:230-243`, reported). The app reads no `user_metadata`, `app_metadata` or `identities` anywhere in `src/`, `scripts/`, `tests/`, `supabase/`, `README.md` (rg, case-insensitive `metadata|identit`: no relevant hit).
- Docs, `auth-identity-linking.mdx:23-25` (raw MDX, reported): "Supabase Auth automatically links identities with the same email address to a single user… It would also be an insecure practice to automatically link an identity to a user with an unverified email address since that could lead to pre-account takeover attacks. To prevent this from happening, when a new identity can be linked to an existing user, Supabase Auth will remove any other unconfirmed identities linked to an existing user."
- **Existing password account confirmed**: same user, Google identity added, password kept. **Existing password account unconfirmed**: `RemoveUnconfirmedIdentities` clears `encrypted_password`, overwrites user metadata and deletes the other identities, then confirms the user if the provider e-mail is verified or autoconfirm is on (`external.go:398-422` re-read for the call and condition; the password clearing is in `models/user.go:1019-1051`, reported). The user id is preserved.
- **Confirm email off**: password sign-ups are auto-confirmed (`signup.go:228-237`, reported), so no unconfirmed password account exists to be cleaned up; per the code, someone who registered a victim's address with a password, without proving the mailbox, keeps that password after the victim signs in with Google (the worker's reading, high confidence on the code path; no live test). The local container runs with `GOTRUE_MAILER_AUTOCONFIRM=true` (`enable_confirmations = false`, `config.toml:209`). The hosted value is not recorded (README.md:254-258 lists only Site URL, Redirect URLs and SMTP; audit item AS7 marks it "unknown").
- `enable_manual_linking` guards only `GET /user/identities/authorize` and `DELETE /user/identities/{id}` (`middleware.go:391-397`, re-read), not `signInWithOAuth` or automatic linking.
- Google-only user, `signInWithPassword`: `400 invalid_credentials` with the generic message, the same as for a wrong password (`token.go:116-118`, re-read). `src/lib/auth-errors.ts:9` maps it to "Invalid email or password."
- `signUp` for an e-mail held by a confirmed user: with `Mailer.Autoconfirm || Sms.Autoconfirm` GoTrue returns `422 user_already_exists`; otherwise HTTP 200 with an obfuscated user, no identities and no e-mail (`signup.go:193-196,281-301`, re-read). Locally `GOTRUE_SMS_AUTOCONFIRM=true`, so local runs always take the error branch; the hosted "Confirm phone" value is unknown. `signup.ts:29` sends the success branch to `/auth/confirm-email`; audit B4 (`context/audits/observability/2026-10-02_check-off-and-uncheck-join-group.md:143`) already recorded the obfuscated case.
- Password reset for a Google user: `/recover` and `updateUser({ password })` work server-side by e-mail lookup (`recover.go:52`, `user.go:150-225`, reported). The app has no reset or `updateUser` call in `src/` (rg: no match), so a Google-created user has no in-app way to set a password.

### 6. The existing app flow (all `file:line` re-read unless marked)

## Architecture Insights

- State-changing auth actions are `POST` forms to `/api/auth/*`, protected by Astro's `checkOrigin`; the two `GET` routes are the e-mail callback and the invite landing, which only set or consume cookies.
- Every returned Supabase `{ error }` goes through `to*ErrorCode` plus `reportMapped`; only codes `unknown`, `forbidden` and `rate_limited` leave a log line, so a new OAuth-specific code would be silent unless the policy is extended.
- Error codes shown to the user are an allow-list of fixed messages (`Object.hasOwn`), never raw provider text; `error_description` from Google or GoTrue is not displayed.
- Redirect targets after auth are hard-coded and there is no `next` mechanism.
- Dashboard-only settings are a recurring failure source (Site URL left at `http://localhost:3000`, `deployment-plan.md:132`; Redirect-URL fallback documented as a rule in `README.md:257`); S-06's plan ordered "add before you remove" (`custom-domain/plan.md:62`).
- The one-time `code` and the PKCE verifier cookie tie a callback to the browser that started the flow; that is also why the e-mail link fails in another browser (`callback.ts:6-8`).
