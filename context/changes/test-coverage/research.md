## Architecture Insights

- **Two seams carry most of the risk, and neither is unit-testable in Vitest as configured.** Astro's runtime (the Origin check, `prerender`, the middleware chain) is exercised only by smoke against the preview build; Vitest tests call handlers with a hand-built `APIContext`. Supabase's RLS is exercised by the 9 real-DB files and the SQL scenarios, while the 7 mocked files pin the handlers' reporting and mapping. A plan that wants Vitest-level proof of the Origin boundary would have to go through Astro's app (`astro preview`/the Cloudflare runtime), which is what smoke already does.
- **One Vitest project, one stack.** The pure rule modules are the cheapest tests in the repo, yet they share the DB-backed global setup, so `npm test`, the end-of-turn hook and Stryker all need `supabase start`. Splitting the config (a unit project without `globalSetup`, or `vitest.configFile` for Stryker only) is the lever that makes mutation runs cheap and parallel-safe; it does not touch application code.
- **Validation is hand-written and duplicated between TS and SQL by design** (`group-rules.ts`/`task-rules.ts` vs the CHECK constraints), with a code-vs-schema parity test that reads the migration file (`task-rules.test.ts:52-61`). S-12 Phase 4 replaces that with DB contract tests; the Stryker targets S-10 names are these same modules.
- **The error contract is fixed and documented.** 302 with an allow-listed `?error=` code for forms; JSON `{ok, error}` with 400/403/404/500/503 for the check-off island; 503 with `Retry-After` on an Auth outage; fixed auth codes never reflecting provider text (`observability-swallowed-errors/plan.md:14,21,131`; S-11 kept it, `dashboard-ui/change.md:118`). E2E and smoke must keep binding to it, not to messages.
- **The release is already ordered; what is missing is proof of compatibility, not ordering.** Build → `db push` → `wrangler deploy` with an approval gate exists; the exposure is the old Worker running against the new schema for the deploy interval and after a failed deploy, which only a "previous release against new schema" job or a canary can prove.
