# Research: Why the claude-review runs on PR #205 posted nothing, and what passes the permission checks

**Date**: 2026-10-19T16:40:57+02:00
**Researcher**: Claude Fable 5.1 (Claude Code session with the owner)

## Research Question

From `context/changes/claude-review-publish/change.md:12-14`: the two `claude-review` runs on PR #205 (39265408742 and 39266174600, 2026-10-19) ended `success` after 19 turns each with `permission_denials_count` 3 and 2 and left no comment on the PR. (1) How can the denied calls be seen, given that `claude-execution-output.json` stays on the runner? (2) What in the prompt or the allow-list (`--allowedTools`) has to change so the summary and the inline comments get posted? (3) Which contracts must a fix keep, and how can rows 2.5–2.8 of the archived plan be re-checked?

## Summary

- **Root cause, reproduced locally.** Claude Code's Bash tool rejects, before any allow rule is consulted, a command whose quoted argument contains a newline followed by `#`. The exact rejection, captured from the `system/permission_denied` stream message of a local probe on Claude Code 2.1.303 (2026-10-19): `Newline followed by # inside a quoted argument can hide arguments from path validation` (probes p2, p3 and q4 in Finding 2). The summary that `.claude/review/claude-review.md:128` mandates has the marker on line 1 and `## Claude review: ` on line 2, so a body passed as `gh pr comment <n> --body '…'` (`:110`) contains that sequence by construction and this one call shape cannot pass on the probed version (2.1.303), whatever the allow-list says; Finding 3 gives the evidence that 2.1.296 in CI behaves the same. The rejection is recorded as a permission denial in `permission_denials` and counted by the action's `permission_denials_count`.
- **It fits the CI observations on Claude Code 2.1.296.** Of the summaries CI posted, the two with the old prompt (PR #116 15:52:13 and PR #117 16:57:38, 2026-10-14) start with `## …` as the first character of the body and have zero lines starting with `#` after line 1; the one with the new prompt (PR #198, 12:37:50, 2026-10-18) uses `<h2>`/`<h3>` HTML headings instead of `## `/`### ` and also has zero such lines (Finding 3). The `ai-review` comments next to them do contain `## ` lines (3 on #116, 2 on #117): a workflow step posts them with `gh api`, so no shell argument is involved. The #198 run (39127947501) logged 3 denials before it posted; the two #205 runs logged 3 and 2 denials and posted nothing. Which commands the #205 runs tried is not in any log (the action prints only the init and result summary), so the identification of those denials with the summary call is an inference, not an observation.
- **Two inaccuracies in the current contract surfaces.** The hide step's jq filter (`.github/workflows/claude-review.yml:93`) matches only bodies starting with `<!-- claude-review:summary -->\n## Claude review: `, so it does not match the `<h2>` summary on #198, and row 2.7 of the archived plan cannot pass on that form. The prompt's tool section (`.claude/review/claude-review.md:21-23`) says `cat`, `head`, `sed` and heredocs are denied; in the local probes under the CI allow-list in default mode, `grep`, `ls`, `find`, `cat`, `head`, `sed -n 1,3p` and `wc` (r1–r7) and the Read tool (r8) ran with zero denials, and a heredoc with a quoted delimiter carrying the full mandated summary shape, an apostrophe, backticks, `$(date)`, `$HOME`, `## ` and `### ` lines passed (q5). A heredoc with an unquoted delimiter is rejected: `Heredoc with unquoted delimiter undergoes shell expansion` (q6).
- **Three ways to see the denied calls, all in the pinned action v1.0.248.** (a) The action output `execution_file` names `${RUNNER_TEMP}/claude-execution-output.json`, the unredacted array of every SDK message, including `system/permission_denied` (with the reason) and the result's `permission_denials` (tool name and full `tool_input`), which `actions/upload-artifact` can keep; GitHub lets "people who are signed into GitHub and have read access to a repository" download artifacts, which for this public repository is every signed-in GitHub user. (b) `show_full_output: true` or `ACTIONS_STEP_DEBUG=true` prints the same messages unredacted into the public job log; the workflow had this flag on 2026-10-14 (run 38592940294) and the review of PR #116 flagged it MEDIUM, so it was removed before the merge. (c) `display_report: true` writes a redacted job step summary with every tool call and its result, truncated at 3,000 characters; it is off by default with a warning about Claude-authored content (Finding 4).
- **Fix candidates the plan can choose from, with the evidence for each** (Finding 6): post the summary through a quoted heredoc (`gh pr comment <n> --body-file - <<'EOF' … EOF`), which passed with the exact contract body and keeps the allow-list, the marker, the hide filter and the README text; or let the model return the summary as `structured_output` through `--json-schema` and post it from a workflow step with `gh api --input`, as `review.yml:248-256` already does for `ai-review`; or switch the headings to HTML and change the filter, which is fragile because a line starting with `#205` trips the same rule (q4). Widening `--allowedTools` does not help: q4 was denied although `gh pr comment 205 …` matched `Bash(gh pr comment:*)`. The action's own comment tool needs tag mode (`track_progress: true`), which prepends the action's header to the comment.
- **Documentation check.** The official pages confirm the pieces around the failure (compound commands split on operators and newlines, a built-in read-only command set, denials in `-p` recorded as `permission_denied` stream messages and in `permission_denials`, Grep and Glob absent from the Linux default tool set, `--setting-sources user` ignoring project settings) but do not describe the newline-followed-by-`#` validation itself (Finding 2).
- **Cost wording.** The runs use the subscription OAuth token (`README.md:523`), so the logged `total_cost_usd` of 0.84 and 0.82 USD is a notional API-price figure, not money spent; the archived research already calls it notional. `context/foundation/open-items.md:90-92` and `change.md:12-14` say each run "kosztuje około 0,8 USD".

### 3. Why the local rule explains the CI history

- Old prompt, 2026-10-14, Claude Code 2.1.296: the summaries posted on PR #116 (15:52:13, 898 chars) and PR #117 (16:57:38, 1,629 chars) both start with `## Review: NEEDS ATTENTION` / `## Code review: APPROVED` as the first character of the body and contain zero lines starting with `#` after line 1 (`issues/116/comments`, `issues/117/comments`, github-actions[bot] comments, 2026-10-19 check). Run 38592940294 (PR #116, `show_full_output: true`) logged three `permission_denied` messages: `This Bash command contains multiple operations. The following part requires approval: sed -n '/Before merge/,$p'` (`decision_reason_type: subcommandResults`, for `gh pr view 116 --json body --jq .body | sed -n '/Before merge/,$p'`), `A group in parentheses in this command can't be checked before it runs` (`other`, for a `--body "…(\`review.yml\`, \`claude-review.yml\`)…"`double-quoted body), and`Path is outside allowed working directories` (`workingDir`, for a Write to `/tmp/review-summary.md`). In the 900 characters of the denied double-quoted body that were read (of 1,038), `#` appears only as its first character; the stated reason was its parentheses, not its heading.
- New prompt, 2026-10-18: the first run with the marker-first shape (39127947501, PR #198) logged 3 denials and then posted a body in which every `## `/`### ` heading of the template (`.claude/review/claude-review.md:112-126`) is replaced by `<h2>`/`<h3>` tags, which is exactly the shape that passes probe q1. The PR #205 runs logged 3 and 2 denials and posted nothing; the model under the same prompt did not reach a passing shape there. Which commands were denied on #205 is not recorded anywhere (Finding 4 explains why), so this is the inference that fits the observations, not a read transcript.
- Consequence for the hide step: `claude-review.yml:93` selects `.body | startswith("<!-- claude-review:summary -->\n## Claude review: ")`; the #198 body starts with `<!-- claude-review:summary -->\n<h2>Claude review: APPROVED</h2>` and is not selected. Row 2.7 of the archived plan ("A second label run on the same PR minimizes the first marked summary", `context/archive/2026-10-18-claude-review/plan.md:335`) cannot pass while the model posts that form. `README.md:533-534` documents the `## Claude review: <VERDICT>` shape and the hide step.

### 5. Agent-mode mechanics that bound a fix

- Mode: `pull_request` with a `prompt` runs in agent mode (`Auto-detected mode: agent`, log line 450); agent mode creates no tracking comment (`src/modes/agent/index.ts:115`, `claudeCommentId: undefined`) and adds no tools of its own, only `--mcp-config` (`:121-132`); `allowedTools` is parsed from the user's `claude_args` (`:92-94,116`).
- MCP servers: `src/mcp/install-mcp-server.ts:84-115` starts `github_comment` (`update_claude_comment`) in agent mode only when the allow-list names `mcp__github_comment__*`; `:150-170` starts the inline server for a PR when the list names `mcp__github_inline_comment__*` or `mcp__github__*` (the case here). `track_progress: true` forces tag mode for `pull_request` and issue events (`src/modes/detector.ts:20-31`), which creates the tracking comment (`src/modes/tag/index.ts:45-47`), merges `Glob, Grep, LS, Read, mcp__github_comment__update_claude_comment, mcp__github_ci__*` and git rules into the allow-list (`:134-161`), appends `--permission-mode acceptEdits` (`:186`) and rewrites the comment header with "Claude finished @user's task in Ns" (`src/github/operations/comment-logic.ts:129-137`).
- Allow-list merging: `base-action/src/parse-sdk-options.ts:16-23,223-241` accumulates every `--allowedTools` occurrence into one de-duplicated set; `:246-264` handles `--disallowedTools`.
- Settings: `base-action/src/setup-claude-code-settings.ts:9-11,62-64` writes `${HOME}/.claude/settings.json` with `enableAllProjectMcpServers: true` and no permission rules; `parse-sdk-options.ts:340-348` turns `--setting-sources user` into `settingSources: ["user"]`, so the repository's `.claude/settings.json` plays no part (log line 527-529 confirms `["user"]`).
- Headless denials: the base action calls the SDK `query()` with no `canUseTool` and no `permissionMode` (`run-claude-sdk.ts:190`; `parse-sdk-options.ts:315-345`), so an `ask` decision is final and lands in `permission_denials` (SDK 0.3.303 `sdk.d.ts:5637`: "Without one (bare -p / SDK query() with no canUseTool), 'ask' decisions are terminal … `result.permission_denials` is the authoritative record"). `run.ts:246` sets `DETAILED_PERMISSION_MESSAGES=1`, undocumented in that repo.

### 6. Fix candidates and what the evidence says about each

Not a plan; the plan picks and sequences.

## Architecture Insights

- Claude Code in headless default mode decides a Bash call in layers: a shape validation that rejects unsafe commands with a stated reason before any rule is read (newline followed by `#` inside a quoted argument; a heredoc with an unquoted delimiter; a parenthesised group; a sub-command that needs approval), then the allow rules by prefix with every part of a compound command checked, with read-only commands and the Read tool allowed without a rule. In `-p` mode without a permission handler every `ask` is a denial, recorded in `permission_denials`, and the model only sees the reason text in its `tool_result`.
- The action keeps the full transcript on the runner by default and prints a sanitized summary; the three disclosure levels (unredacted log, unredacted artifact, redacted step summary) are all explicit inputs or outputs, with warnings for the unredacted ones. In a public repository each of them is readable by every signed-in GitHub user, so the choice is between redaction and completeness, not between public and private.
- A posting contract that relies on the model emitting a markdown body through a shell argument inherits the shell's quoting rules and Claude Code's validation layer; the two shapes that avoid them are a quoted heredoc (the body never becomes an argument) and a workflow step that posts structured output (the body never passes through the model's shell at all), which is how `ai-review` already works.
